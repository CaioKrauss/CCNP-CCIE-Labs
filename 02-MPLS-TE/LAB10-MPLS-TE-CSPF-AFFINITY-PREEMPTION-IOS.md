# LAB 10 — MPLS Traffic Engineering: Dynamic CSPF, Bandwidth, Affinity and RSVP-TE Preemption

**Platform:** four Cisco 7206VXR / IOS 15.2(4)S7 in a separate EVE-NG lab called `CSPF.unl`.
**Date:** 2026-11-16.
**Scope:** control-plane routing/TE TED, RSVP reservation and signaling, path changes verified using traceroutes, priority-based preemption and recovery.
**Status:** all four exercises validated. The stable final configuration leaves the high-priority Tunnel200 administratively shut, allowing Tunnel100 to remain established.

## Goal and topology

Demonstrate four distinct RSVP-TE path decisions in the same four-node diamond without treating shortest-path IGP, dynamic CSPF, administrative constraints and RSVP preemption as equivalent mechanisms.

```text
                  R2 2.2.2.2
                /            \
      Fa0/0 10 /                \ 10 Fa0/0
              /                  \
     R1 1.1.1.1                  R4 4.4.4.4
              \                  /
      Fa1/0 30 \                / 10 Fa1/0
                \            /
                  R3 3.3.3.3

      via R2: metric 10 + 10 = 20
      via R3: metric 30 + 10 = 40
```

| Directed link | Local router interface/IP | Neighbor interface/IP | IS-IS / TE metric | Final TE attribute flag |
|---|---|---|---:|---|
| R1 ↔ R2 | R1 Fa0/0 10.0.12.1/30 | R2 Fa0/0 10.0.12.2/30 | 10 | `0x0` |
| R2 ↔ R4 | R2 Fa1/0 10.0.24.1/30 | R4 Fa0/0 10.0.24.2/30 | 10 | `0x0` |
| R1 ↔ R3 | R1 Fa1/0 10.0.13.1/30 | R3 Fa0/0 10.0.13.2/30 | 30 | `0x1` |
| R3 ↔ R4 | R3 Fa1/0 10.0.34.1/30 | R4 Fa1/0 10.0.34.2/30 | 10 | `0x1` |

All router transport interfaces use IS-IS CORE level 2, RSVP-TE extensions, LDP and 10,000 kbps RSVP reservable bandwidth **in the final snapshots**. Loopback0 on R1/R2/R3/R4 is `1.1.1.1/32` / `2.2.2.2/32` / `3.3.3.3/32` / `4.4.4.4/32`. These are lab-only addresses and not production recommendations.

## Stage 1 — Dynamic CSPF picks the lower-metric eligible path

Head-end R1 creates an RSVP-TE tunnel for R4 using a **dynamic** path option rather than a user-specified explicit path:

```cisco
interface Tunnel100
 description CSPF-DYNAMIC-R1-TO-R4
 ip unnumbered Loopback0
 tunnel mode mpls traffic-eng
 tunnel destination 4.4.4.4
 tunnel mpls traffic-eng autoroute announce
 tunnel mpls traffic-eng priority 7 7
 tunnel mpls traffic-eng bandwidth 1000
 tunnel mpls traffic-eng path-option 1 dynamic
```

**Owner-observed output:** `Admin up / Oper up`, `path weight 20`, `OutLabel FastEthernet0/0, 16`, `Next Hop 10.0.12.2`. RSVP ERO generated by CSPF was `10.0.12.2 10.0.24.2 4.4.4.4`; traceroute showed **R1→R2→R4** with MPLS label 16. A generated RSVP `Explicit Route:` in `show mpls traffic-eng tunnels` **does not mean** the operator configured a strict ERO.

R1's route to `4.4.4.4/32` remained an IS-IS route but resolved through **Tunnel100** because of `autoroute announce`.

## Stage 2 — CSPF rejects a lower-cost path due to bandwidth

Owner temporarily changed RSVP reservable bandwidth on **R1 Fa0/0 toward R2** from `ip rsvp bandwidth 10000 10000` to `ip rsvp bandwidth 500 500`, then requested `mpls traffic-eng reoptimize`.

The tunnel still needed **1000 kbps**. R1→R2 had only **500 kbps** reservable, so CSPF chose the higher-cost R1→R3→R4 path. Observed: `path weight 40`, Fa1/0, label 21, next-hop `10.0.13.2`, and traceroute via `10.0.13.2` / `10.0.34.2`.

On restoration of `ip rsvp bandwidth 10000 10000` on R1 Fa0/0, the dynamic tunnel reoptimized back to R1→R2→R4 with weight 20 and new RSVP instance 18. This tests RSVP reservation constraints, **not** physical Ethernet speed or packet shaping.

## Stage 3 — Affinity/admin group enforces a policy

Owner set `mpls traffic-eng attribute-flags 0x1` on both directions of R1–R3 and R3–R4, and set this matching mask on R1 Tunnel100:

```cisco
interface Tunnel100
 tunnel mpls traffic-eng affinity 0x1 mask 0x1
```

For each link, CSPF checks `(link_attributes & mask) == (tunnel_affinity & mask)`. Here the low-cost path via R2 has `0x0` and is ineligible; via R3 both directed links have `0x1` and are eligible. The actual R1 tunnel reported **`Affinity: 0x1/0x1`**, **path weight 40**, next hop **`10.0.13.2`**, RSVP LSP instance **19**. This choice is due to **policy**, not bandwidth scarcity.

Pitfall from the exercise: `tunnel mpls traffic-eng affinity` belongs on the RSVP-TE **head-end tunnel interface** on R1, not on the tail-end R4, where only physical-link `attribute-flags` were needed.

## Stage 4 — RSVP-TE priority-based preemption

The two RSVP LSPs compete for the **same directed R3→R4 link** with only **10,000 kbps reservable**:

| RSVP LSP | Head-end | Destination | Bandwidth | Setup/Hold priority | Affinity | Path |
|---|---|---|---:|---|---|---|
| `Tunnel100` | R1 | R4 | 8,000 kbps | 7/7 (low) | `0x1/0x1` | R1→R3→R4 |
| `Tunnel200` | R3 | R4 | 5,000 kbps | 0/0 (high) | `0x1/0x1` | R3→R4 |

R1 Tunnel100, when first increased from 1 to 8 Mbps, stayed **UP** and received RSVP instance 21. R3's TED for outgoing **Fa1/0→10.0.34.2** then showed **8000 kbps allocated at priority 7**, **2000 kbps remaining** at priority 7; priority 0 could still see the full 10000 kbps because RSVP can preempt lower-priority LSPs. These values represent *reservable/preemptible* capacity, not physical bandwidth.

### Deliberate initial error: an affinity mismatch

R3 Tunnel200 was initially created with default `Affinity: 0x0/0xFFFF`, incompatible with R3→R4's `attribute-flags 0x1`. Owner observed `Admin up / Oper down / Path not valid`, then corrected it on R3:

```cisco
interface Tunnel200
 tunnel mpls traffic-eng affinity 0x1 mask 0x1
```

With the correction, Tunnel200 became **UP**, dynamic path weight 10, outgoing Fa1/0 to R4, with **5000 kbps** reserved and no Autoroute. The preexisting low-priority Tunnel100 became **DOWN / Path not valid**, its reservation was absent, and R3's TED showed **5000 kbps** allocated at priority 0, **5000 kbps** available at priority 7.

The owner then explicitly repeated the event by shutting/re-enabling R3 Tunnel200. **R3 syslog directly identified the preemption:**

```text
*Nov 16 05:41:43.259: %MPLS_TE-5-LSP: LSP 1.1.1.1 100_34: DOWN: preempted on Fa1/0  Reason: insufficient resources
*Nov 16 05:41:43.271: %LINEPROTO-5-UPDOWN: Line protocol on Interface Tunnel200, changed state to up
```

RSVP priority is ordered **0 (highest) through 7 (lowest)**. Setup priority governs whether a new LSP may preempt another; hold priority affects resistance to preemption. The observation demonstrates **reservation/control-plane preemption**, not a measured zero-loss data-plane transition.

## Stage 5 — Resource release and recovery

The owner administratively shut R3 `Tunnel200`, releasing its high-priority reservation. R1 Tunnel100 automatically reestablished with **8 Mbps** via R3 and the following observed output:

```text
R1#show mpls traffic-eng tunnels
Admin: up         Oper: up     Path: valid       Signalling: connected
path option 1, type dynamic (Basis for Setup, path weight 40)
Bandwidth: 8000 kbps (Global) Priority: 7 7 Affinity: 0x1/0x1
OutLabel: FastEthernet1/0, 22
Next Hop: 10.0.13.2
Tun_Instance: 44
Explicit Route: 10.0.13.2 10.0.34.2 4.4.4.4
R1#show ip rsvp reservation
4.4.4.4 1.1.1.1 0 100 44 10.0.13.2 Fa1/0 SE LOAD 8M
```

The **final collected R3 running-config and startup-config both contain `shutdown` under Tunnel200**. They preserve the safe recovery state: low-priority Tunnel100 can operate. Re-enabling Tunnel200 is expected to repeat the resource conflict.

## What to verify in this lab

```cisco
show isis neighbors
show mpls traffic-eng topology
show mpls traffic-eng tunnels
show ip rsvp reservation
show ip route 4.4.4.4
traceroute 4.4.4.4
show logging
```

- In the **TED**, find the directed link `Intf Address: 10.0.34.1` / `Nbr Intf Address: 10.0.34.2` and review RSVP reservable bandwidth by priority.
- On **R1**, check whether Tunnel100 is **UP** or **DOWN**, whether Autoroute is enabled, and whether its next hop matches dynamic CSPF.
- On **R3**, inspect the local `Tunnel200` state, 5 Mbps reservation, and preemption syslog. Confirm the intended saved shutdown when done.
- Do not infer that an UP tunnel carries an application flow unless data-plane probes/counters exist; early stages have traceroute observations, while preemption was assessed from RSVP and TE signaling.
